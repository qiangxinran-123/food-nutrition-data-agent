更新日期：2026-11-01  
交付范围：数据准备、数据质量检测、数据清洗、清洗后复检、人工查看副本。  
不包含：聚类算法本身、聚类结果评价、智能体编排界面。

> 本文档面向第一次接手项目的同学。先看“交付结论”，再看“目录说明”，最后按需要查看检测、清洗和复现章节。

> `0.1–0.3` 保留为 `v2` 保守基线的说明。2026-11-01 新增的正式清洗版本、策略链和复检结果见 `0.4`；后续聚类和建模应使用 `v5`。

## 0. 交付结论

### 0.1 不同任务应该拿哪个文件

| 要做什么 | 使用哪个文件 | 不要做什么 |
|---|---|---|
| 查看数据、向老师演示 | `outputs/off_52k_v2_view/off_52k_v2_cleaned.xlsx`（旧版示例，不是 v5） | 不要拿旧 Excel 和 v5 parquet 混用 |

### 0.2 `v2` 历史保守基线

- 历史基线版本：`off_52k_v2`；当前正式版本见 `0.4` 的 `off_52k_v5`
- 数据：50,000 行 × 20 列
- 业务字段：18 个
- 技术字段：2 个，分别是 `__row_id`、`__source_row`
- `code` 重复：0
- 10 个核心营养数值字段空值：0
- 清洗计划：53 个决策，状态 `success`
- 自动化测试：65 个，全部通过
- 原始 `v1` 文件没有被覆盖

### 0.3 交付时必须主动说明的限制

`v2` 是“可复现、可审计的保守清洗基线”，不是“每个值都经过人工确认的真值表”。它解决了结构、重复和数值空缺问题，但以下问题被有意保留或只做标记：

1. 异常值没有被截断或删除；
2. 字段冲突没有被强行判定谁对谁错；
3. 非标准条码没有改写；
4. 文本缺失没有强行猜测；
5. `unknown` 不是合法 Nutri-Score 类别，不能当真实标签训练；
6. 原数据中的 0 值存在“真实为零”和“缺失占位”两种可能，`v2` 没有擅自把所有 0 改掉。

其中第 6 点尤其重要：`v2` 的数值缺失清洗使用的是“公式推导 + 中位数兜底”，不是用 0 填充。112,735 个补齐值中只有 2 个为 0，且都是由原始能量为 0 推导出来的。Excel 中大量 0 主要来自原始数据。当前数据中约有 1,300 行存在逻辑可疑的 0，例如能量为 0 但蛋白质或碳水大于 0、总脂肪为 0 但饱和脂肪大于 0。正式做聚类前，应把这类 0 作为已知风险写入报告，或另建 `v3` 处理，不能宣称它们已经全部清洗正确。

### 0.4 2026-11-01 正式清洗修订版 `v5`

当前正式交付版本改为 `off_52k_v5`，不再使用 `v2` 作为最终聚类输入。`v2` 仍保留用于前后对照和审计。

| 项目 | 当前文件或结果 |
|---|---|
| 聚类/建模数据 | `data/processed/off_52k_v5.parquet` |
| 字段规则 | `config/profiles/off_52k_v5.json` |
| 版本清单 | `data/processed/off_52k_v5.manifest.json` |
| 最终变更日志 | `data/processed/change.off_52k_v5_precision_finalization.changes.parquet` |
| 清洗后复检 | `logs/checks_v5/off_52k_v5_quality_summary.md` |
| 完整策略链 | `config/plans/off_52k_v3_stratified_repair.json` → `off_52k_v4_convergence.json` → `off_52k_v5_precision_finalization.json` |

本轮不是把所有异常一刀切，而是按问题性质分层处理：

1. **明显不可能的硬范围值**：例如每 100 克超过 100 克、能量小于 0。先把原值写入隔离表，把单元格置空，再用配对字段公式或中位数补齐。
2. **箱线图统计尾部**：不删除行，只把超出的值截断到该字段检测出的上下界；第二轮复检后按新分布再截断一次。
3. **能量千卡/千焦、盐/钠冲突**：以千焦和钠为主字段，重算千卡和盐，保证单位换算关系成立。
4. **糖/碳水、饱和脂肪/总脂肪冲突**：不丢行，把子字段压到父字段允许的上界 `parent * 1.05 + 0.5`。
5. **盐/钠箱线图截断**：先按盐的上界反推钠的上界，再重算盐，避免截断后重新产生冲突。

`v5` 复检结果：

| 检测项 | v2 复检 | v5 复检 |
|---|---:|---:|
| 重复数据 | 0 | 0 |
| 硬范围违规 | 1,036 个单元格 | 0 |
| 箱线图统计尾部 | 4,971 个单元格 | 0 |
| 字段冲突涉及行 | 3,169 | 0 |
| 缺失单元格 | 173,016 | 173,016 |
| 非标准条码行 | 197 | 197 |

`v3 → v5` 共修改 12,909 个单元格，没有删除任何行。文本缺失、非标准条码、不可用标签和类别不平衡仍然保留并继续报告，因为这些不能靠“异常值截断”解决。

## 1. 整体流程

项目按下面的顺序工作：

1. 原始 Excel 放入 `data/raw/`，供人查看和追溯。
2. 冻结为 `data/base/off_52k_v1.parquet`，作为只读机器快照。
3. 七个检测工具检查 `v1`，输出 JSON、Markdown 汇总和完整选择表。
4. 大模型或人根据选择表选择策略，形成 `config/plans/` 下的清洗计划。
5. 七个清洗工具按分层计划执行，生成 `v3`、`v4`、`v5` 的 parquet、manifest、变更日志和新 profile。
6. 七个检测工具再次检查 `v5`，输出 `logs/checks_v5/`。
7. 人工查看版从正式 parquet 导出为 Excel，只用于查看，不参与机器读取。
8. 聚类与评价同学使用 `off_52k_v5.parquet` 和 `off_52k_v5.json` 继续工作。

核心原则：**检测只找问题，清洗才改数据；清洗必须产生新版本；每个改动必须能追溯。**

### 2.6 `logs/`：检测与清洗审计

#### `logs/checks/`：清洗前 `v1` 检测

包含：

- `off_52k_v1_duplicates.json`：重复数据检测；
- `off_52k_v1_outliers.json`：异常值/噪声检测；
- `off_52k_v1_types_formats.json`：类型与格式检测；

  `selection.off_52k_v1.missing.brands.parquet`、
  `selection.off_52k_v1.duplicate.primary_key.parquet`。

JSON 报告中的 `sample` 是抽样预览，完整受影响行必须从 `selection_artifact_id` 指向的 Parquet 选择表读取。

#### `logs/checks_v2/`：清洗后 `v2` 复检

文件名结构与 `logs/checks/` 相同，只是前缀改为 `off_52k_v2_`。当前共有 33 个选择表。
这些报告用于回答两个问题：

1. 清洗有没有解决目标问题，例如重复是否归零；
2. 清洗有没有制造新问题，例如补齐后是否出现新的冲突或异常尾部。

`logs/checks_v2/off_52k_v2_quality_summary.md` 是最适合直接查看的复检总览。

| 类别 | 字段 | 用途 |

| 实体标识 | `code` | 商品条形码，文本类型，用于实体匹配；不能当连续数值 |

`code` 是条码文本，不是数值特征。把它转成整数会丢失前导零，也会把“编号”错误地当成“大小”。

### 3.3 本次数据为什么不是原有 19 个字段

`no_nutrition_data` 已从交付数据中删除，不列入 18 个业务字段。营养是否缺失由 10 个营养字段自身以及检测结果表达，不再额外保留一个容易与缺失判断重复的标志列。

因此对外应统一表述为：

- **18 个业务字段**；
- 另有 **2 个技术字段**；
- parquet 和 Excel 一共显示 **20 列**。

## 4. 新增字段及原因

在冻结 `v1` 时新增了两个以双下划线开头的技术字段。它们不是营养业务指标，也不应作为聚类距离特征。

| 字段 | 逻辑类型 | 为什么新增 | 实际用途 |
|---|---|---|---|
| `__row_id` | 标识符/文本 | 清洗会删行、重排和生成新版本，Excel 行号不再稳定 | 在检测选择表、清洗决策和变更日志之间稳定定位同一行 |
| `__source_row` | 标识符/数值 | 去重后行号会发生偏移，需要回到原始 Excel 核对 | 记录原始 Excel 行号，便于人工追溯 |

举例：某个缺失值在 `v1` 中的 Excel 行号是 12345，去重后它在 `v2` 中的位置可能已经不是 12345。`__row_id` 保证后续步骤仍能找到这一行，`__source_row` 保证人能回到原表核对。

这两个字段在 manifest 和 profile 中都有明确角色，不参与统计插补，也不会被当作普通营养数值计算。

## 5. 检测工具

### 5.1 检测器的共同约定

- 检测器只读数据，不修改数据。
- 所有列名、单位、范围、约束和标签规则来自 profile。
- 每个问题产生 `finding_id`，并生成完整选择表 `selection_artifact_id`。
- 报告里的 `sample` 只用于展示，不能拿来执行清洗；真正清洗必须读取选择表。
- 同一个检测器换到别的数据集时，只需提供新的 profile。

### 5.2 七个检测器

| 检测工具 | 代码 | 检测内容 | 主要输出 |
|---|---|---|---|
| 缺失值检测 | `checks/missing.py` | 空值、空字符串、profile 声明的缺失 token；统计单元格数、行数、比例和严重程度 | `*_missing.json`、`selection.*.missing.*.parquet` |
| 重复数据检测 | `checks/duplicates.py` | 按 profile 的主键规则找重复组；当前数据集按 `code` 判断；给出可保留/可删除候选 | `*_duplicates.json`、`selection.*.duplicate.*.parquet` |
| 异常值/噪声检测 | `checks/outliers.py` | 业务硬范围违规；IQR 统计尾部；默认倍数 5，比常见的 1.5 更宽，避免把真实高营养食品轻易判错 | `*_outliers.json`、`selection.*.outlier.*.parquet` |
| 类型与格式检测 | `checks/types_formats.py` | 逻辑类型是否匹配、数值是否有限、条码是否符合 8/12/13/14 位数字正则；保留前导零 | `*_types_formats.json`、`selection.*.format.*.parquet` |
| 字段冲突检测 | `checks/conflicts.py` | 能量 kcal/kJ 换算、盐/钠换算、糖不超过碳水、饱和脂肪不超过总脂肪 | `*_conflicts.json`、`selection.*.conflict.*.parquet` |
| 标签错误检测 | `checks/labels.py` | 标签是否合法、是否是不可用 token、是否存在别名、各类数量是否异常 | `*_labels.json`、`selection.*.label.*.parquet` |
| 类别不平衡检测 | `checks/imbalance.py` | 类别计数、少数类占比、最大类/最小类比例，是否达到风险阈值 | `*_imbalance.json`、`distribution.*.parquet` |

### 5.3 检测输出怎么读

每个 JSON 报告至少包含：

- 检测器名称和版本；
- 状态 `success`；
- 数据集引用；
- 检查的列和行数；
- findings 列表；
- 每个 finding 的规则、严重程度、受影响数量、比例、样例和选择表 ID。

`logs/checks/` 是清洗前 `v1`，`logs/checks_v2/` 是清洗后 `v2`。
当前 `v1` 有 45 个选择表，`v2` 有 33 个选择表。选择表多不等于数据更差，它表示工具为每个可执行问题都留下了完整定位。

### 5.4 当前没有单独覆盖的情况：可疑 0 值

当前的缺失检测只把空值、空字符串和 profile 声明的 token 当缺失。数字 0 在 profile 中位于合法范围内，因此会按真实观测值保留。

这会带来一个已知风险：

- 食品营养里的 0 可能是真的（无糖、无脂、无纤维）；
- 也可能是录入时用 0 代替“未填写”；
- `v2` 没有擅自判断，也没有把所有 0 改成中位数。

后续如要继续提升聚类质量，建议在 `v3` 增加“可疑零值”检测规则，例如：

- 能量为 0，但蛋白质/脂肪/碳水大于 0；
- 总脂肪为 0，但饱和脂肪大于 0；
- 碳水为 0，但糖大于 0；
- 盐为 0，但钠大于 0。

这类 0 应先标记为可疑，再按品类中位数或公式处理，而不是全表统一替换。

## 6. 清洗工具

### 6.1 共同约束

- 清洗必须从检测选择表出发，不能直接处理报告样例。
- 默认 `dry_run=true`；真正写入必须明确 `--no-dry-run`。
- 删除行、覆盖标签、批量插补等高风险动作需要额外确认。
- 标识符禁止统计插补，避免给条码补出一个不存在的商品。
- 标签不能使用普通数值插补器，不可用标签与非法标签分开处理。
- 每个动作产生 ChangeSet、逐单元格变更记录和新 manifest。
- 清洗永远生成新版本，不覆盖 `v1` 或已有正式版本。
- 大模型负责选择策略和参数，真正执行的是确定性的 Python 代码，不执行模型临时生成的代码。

### 6.2 七个清洗器

| 清洗工具 | 代码 | 代表策略 | 适用情况 |
|---|---|---|---|
| 缺失值清洗 | `cleaning/fill_missing.py` | `keep_missing`、`drop_row`、`fill_constant`、`impute_statistic`、`impute_grouped`、`derive_from_formula`、`quarantine_cell`、`quarantine_row`；`impute_model` 仅登记，尚未实现 | 数值缺失、文本缺失；优先使用公式或分组/全局统计量 |
| 重复数据清洗 | `cleaning/remove_duplicates.py` | `keep_first`、`keep_last`、`keep_most_complete`、`keep_by_quality`、`keep_by_priority`、`merge_group`、`quarantine_group`、`no_action` | 主键重复或业务上重复的记录组 |
| 异常值/噪声清洗 | `cleaning/handle_outliers.py` | `flag_only`、`clip_value`、`set_null`、`quarantine_cell`、`quarantine_row`、`drop_row`、`recompute_by_formula`、`correct_unit_or_scale` | 先判断是真极端值还是错误值，再决定是否处理 |
| 类型与格式清洗 | `cleaning/normalize_types_formats.py` | `trim_whitespace`、`normalize_case`、`cast_numeric`、`cast_datetime`、`map_boolean`、`preserve_identifier_as_text`、`normalize_date_format`、`set_invalid_null`、`quarantine_invalid`、`leave_unchanged` | 数字存成文本、日期格式、前后空格、条码前导零等 |
| 字段冲突清洗 | `cleaning/resolve_conflicts.py` | `flag_only`、`recompute_derived`、`trust_primary_source`、`null_conflicting_cells`、`quarantine_row`、`no_action`；`custom_resolver` 未实现 | 两个字段之间违反换算或业务关系 |
| 标签清洗 | `cleaning/repair_labels.py` | `canonicalize_alias`、`mark_unavailable`、`exclude_from_training`、`map_deterministic_value`、`quarantine_invalid`、`relabel_by_rule`、`no_action` | 标签拼写、别名、不可用标签、非法标签 |
| 类别不平衡处理 | `cleaning/mitigate_imbalance.py` | `report_only`、`class_weight`、`stratified_split`、`oversample_minority`、`undersample_majority`、`collect_more_samples`、`no_action` | 少数类过少；正式基线优先权重或分层，不复制样本 |

清洗工具只负责执行策略，不替用户决定“哪个策略一定正确”。策略选择依据是字段含义、缺失机制、业务规则和下游任务。

### 6.3 为什么工具不局限于当前数据集

工具代码中没有写死 `off_52k_v2` 的字段名和范围。它们从 profile 读取：

- 哪一列是实体 ID；
- 哪些列是数值、文本、类别或标签；
- 数值允许范围；
- 什么 token 算缺失；
- 什么列组合算重复；
- 哪些字段之间必须满足什么关系；
- 哪些标签值不可用；
- 类别不平衡阈值。

换数据集时，主要工作是准备新的 profile 和清洗计划，而不是重写七个检测器和七个清洗器。

## 8. 关于 0 值的核实结论

这是本次交付最容易被误解的地方。

### 8.1 0 不是中位数填充的默认值

- 112,735 个补齐单元格中，只有 2 个补成了 0；
- 其余 112,733 个补齐值都不是 0；
- 两个 0 都来自原始能量为 0，再按 `kcal = kJ / 4.184` 推导；
- 因中位数补齐产生的 0：0 个。

### 8.2 大量 0 来自原始数据

当前 `v2` 的主要零值比例：

| 字段 | 0 的单元格数 | 占 50,000 行 |
|---|---:|---:|
| `energy-kcal_100g` | 1,030 | 2.06% |
| `energy_100g` | 1,026 | 2.05% |
| `proteins_100g` | 5,308 | 10.62% |
| `fat_100g` | 6,540 | 13.08% |
| `saturated-fat_100g` | 9,152 | 18.30% |
| `carbohydrates_100g` | 3,226 | 6.45% |
| `sugars_100g` | 6,496 | 12.99% |
| `fiber_100g` | 6,169 | 12.34% |
| `salt_100g` | 5,632 | 11.26% |
| `sodium_100g` | 5,630 | 11.26% |

### 8.3 目前确认的可疑零值

按四条硬规则检查，约 1,300 行存在逻辑冲突：

- 413 行能量为 0，但蛋白质/脂肪/碳水至少一个大于 0；
- 852 行总脂肪为 0，但饱和脂肪大于 0；
- 285 行碳水为 0，但糖大于 0；
- 15 行盐为 0，但钠大于 0。

另有 167 行 10 个营养字段全为 0。其中矿泉水、茶等可能合理，但香料、芝麻等明显可疑。

### 8.4 交付口径

`v2` 可以用于结构验收和保守聚类基线，但不能在汇报中声称“所有 0 都是真实值”。
如果要做正式聚类对比，建议：

1. 先用 `v2` 做基线；
2. 在报告中列出零值风险；
3. 另建 `v3`，只处理逻辑上不可能的 0，保留真实的无糖、无脂、无纤维值；
4. `v3` 不覆盖 `v2`，并重新生成 manifest、profile 和复检报告。

### 9.2 聚类时怎么使用字段

- `code`：实体标识，不是数值特征，不能参与距离计算；
- `__row_id`、`__source_row`：追溯字段，不参与聚类；
- 10 个核心营养数值：主要连续特征；
- `nutriscore_grade`：外部标签，不是普通聚类输入；
- `product_name`、`brands`、`categories`、`categories_en`、`serving_size`：文本或类别信息，是否使用由聚类方案决定；
- `serving_quantity`：单位由来源决定，使用前必须确认单位，不要直接与其他营养数值混用。

标准化、特征选择、是否做对数变换、K 值选择等属于聚类同学的工作范围，本部分工具不替他决定。

### 9.3 补齐值怎么识别

10 个核心营养数值没有空值，但其中 112,735 个单元格由推导或中位数补齐。要区分原始值和补齐值，可读：

```text
data/processed/change.off_52k_v2_conservative.changes.parquet
```

关键列：

- `row_id`：对应哪一行；
- `column`：哪一列；
- `new_value`：补成什么；
- `reason`：公式还是中位数；
- `is_imputed`：是否为补齐值；
- `change_type`：删除、补齐或其他变更。

如果聚类对补齐敏感，可以用 `is_imputed` 做敏感性分析，或在报告中说明补齐比例。

### 9.4 标签和评估

- 可用 `nutriscore_grade`：21,978 行；
- 不可用标签：28,022 行；
- 非法标签：0；
- 训练排除表：
  `logs/cleaning/off52k_v2.label.exclude_from_training.nutriscore_grade.training_exclusions.parquet`；
- 类别权重：
  `logs/cleaning/off52k_v2.imbalance.class_weight.class_weights.parquet`。

如果评价阶段把 Nutri-Score 作为外部参照，必须排除不可用标签，不能把 `unknown` 当成一个真实类别计算准确率。

### 9.5 给聚类同学的一句话

先用 `v2` 跑保守基线，但必须同时检查 `is_imputed`，并在报告中写明零值风险；不能把补齐值或可疑 0 当作真实测量差异解释。
